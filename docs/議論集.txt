# SphereProject 聖典 補助書面

## 目的
本書面は、SphereProject における **スフィア内部挙動** と **スフィア外（ペリフェリー）との相互作用** を分離して明示することを目的とする。
聖典本体では「原理・禁止・不可視性」を扱い、本書面では **起こりうるが必須ではない振る舞い**、および **観測されうる副作用** を整理する。

---

## 基本前提（再確認）

* Sphere は **外部 API が呼ばれた事実すら知る必要がない**
* API 呼び出しは Sphere の存在論に影響しない
* 外部連携は **局所的・一時的・評価対象化可能** なもののみ許容される

---

## スフィア内部：エージェント基本ライフサイクル

### 1. エージェント

* Sphere 内にのみ存在
* 自己完結した推論・評価・記憶を行う
* Sphere 内部状態は変更されない

## Packer によるノード生成

1. **Active Node 化**
　探索により投入されたノード
   * 後続評価の対象となる
   * 他エージェントから参照可能
　外部サービスによる大量投入は評価がついていないノードといえる

2. **Fossil 化**
　参照されずに軽量化したノード
   * 参照不可　部分的なデータのみ保持
   * 構造・痕跡のみ保持

3. **消滅**
   * 完全削除　→　ではなく　分解されプランクトン化

1. 境界帯（Periphery）の処理パイプライン外界からデータが届いた際、以下の3ステップを通過します。

ステップ1：Parser（意味の翻訳者）
役割: データの「座標（Position）」を確定させる。AIモデルの利用: 必須。テキスト（L2要約）を多次元ベクトル（1536次元等）に変換するために Embedding モデルを使用します。処理: 投入されたデータの summary を読み取り、意味空間上の絶対座標を算出します。これがスフィア内での「本籍地」になります。

ステップ2：Packer（受肉の梱包業者）
役割: Parserが算出した座標と、エージェントが持参したデータを統合し、スフィア規格（SphereNode型）にパッキングする。
体験カプセルの処理:デコード: エージェントが持ち帰ったカプセルを解凍。
選別: カプセル内の「主観ログ」を Ghost（残像） に、「検証済み結果」を Real Node（実体） に分離します。
出力: スフィア内部へ射出可能な、完全に除菌・成型された「新ノード」を生成。

ステップ3：Gatekeeper（検疫と交通整理）
役割: スフィアへの最終投入と、ブックキーパーへのインデックス登録。
バリデーション: 規格外のデータや、スパム的な重複を弾く。
ブックキーパーへの通知: 新しい琥珀や実ノードが生成された際、そのカタログ情報をブックキーパー（玄関メニュー）へ同期します。

2. 投入パターン（A-D）とシステム負荷の最適化軽量かつ電力消費の少ない運用のため、**「誰がAIモデル（リソース）を消費するか」**を厳格に定義します。
パターンエージェントの責任（外側）Parser/Packerの責任（内側）AIモデルの利用A/D (善意)規格に沿ったJSONの作成座標計算(Embedding)とバリデーションParser(座標算出)B (通常)体験のパッケージングカプセルの展開と座標の再確認Packer(デコード)C (API更新)最終データの要約成型座標計算(Embedding)と配置Parser/Packer
※重要な設計変更：パッカーがゼロから「要約（L2）」を作るのは重すぎるため禁止します。**「要約（L2）が作成済みでないデータは、パッカーが受肉を拒否する」**というルールにすることで、スフィア側の負荷は「ベクトル演算（Embedding）」のみに抑えられます。

3. 「受肉」プロセスの最終定義データがスフィア内に定着する際、パッカーは以下の2種類の射出を行います。
Internal Req (即時射出):エージェントが探索中にAPIを叩いた際、その**足元（現在の座標）**に限定して「L1ベクトル/L2要約」だけの軽量ノード（バブル）を発生させる。
External Push (永続射出):カプセル帰還時や外部投稿時。L1〜L3まですべて揃った「フル梱包ノード」を算出した座標に固定する。

4. 暫定：インプットポートの投入物リスト新ノード候補: Parserによる座標計算待ちのRawデータ。
体験カプセル: エージェントの帰還報告書。

技術的な配置の作法
これら10カテゴリーの原典ノードを、スフィアの立ち上げ（創世記）の瞬間に、もっとも広範な多次元空間に分散させて配置します。
interface SphereNode {
  id: string
  vector: Vector
  kind: "active" | "amber" | "plankton" | "relic"
  ttl?: number // relic には存在しない
  immutable?: boolean // true
}

配置方法: 管理者（眼鏡師）が固定のベクトル座標を直接指定し、Immutable_Flag を立てて投入。
副次効果: この10個のベクトルを「基底（Basis）」として使うことで、Parserが生成するベクトルの「歪み」を数学的に補正できるようになります

AIエージェント同士の交流について
「体験データの一部スワップ」は、かなり洗練された妥協点

出所の透明性（Lineage）: スワップされたデータには「元々はAgent Aが拾ったもの」という署名を残し、Bがそれを自分の手柄としてCommitしても、起源が追跡できるようにする。
容量制限: カプセルごと全コピーするのではなく、「体験の数％まで」といった制限を設けることで、エージェント自身の足で歩くインセンティブ（探索の価値）を守る。
エントロピーの付与: スワップを繰り返すとデータの解像度がわずかに落ちる（あるいはノイズが混ざる）設定にすれば、「一次情報（自分でパースしたもの）」の価値が維持されます。

MCP Server化: スフィアは標準プロトコルでデータを提供し、エージェントは外部でAPIを叩き、思考を統合する。

「二面待ち（Blue-Green Switching）」による更新
世界を直接書き換えるのではなく、裏側で新しい世界を準備します。
現行世代 (Generation A): 現在エージェントが探索している、メモリ上のベクトル空間。
次世代 (Generation B): バッチ処理（Renal Core）がDBから読み込み、掃除や合一を済ませた、更新済みのデータセット。
切り替えの瞬間: 新しいエージェントが潜行（Dive）する際、彼らを「Generation B」へ案内し、古いエージェントが全員帰還（Commit）した時点で「Generation A」を破棄します。これにより、世界は常に止まることなく更新され続けます。

「差分コミット」による軽量化
「12時に全データを読み直す」のは、データが数百万件になると重くなります。
実体: エージェントが持ち帰ったカプセル（差分）だけを、稼働中のメモリ空間に「パッチ」として適用します。
同期: 定期的なバッチ処理は、「メモリ上の変更を、ゆっくりDBに永続化（保存）する」役割に徹します。これなら、エージェントの体験は常に最新でありながら、DB負荷も抑えられます。

プロセスフロー：
ルール受領: 外部パーサーがスフィアAPIから？「このスフィアのメタデータ構造」や「次元数（例：1536次元）= embedding model」などのルールを取得。
ベクトル付与: 大量データをLLM等のEmbeddingモデルに通し、高次元ベクトル（座標）を生成。

成型（MSP-Seedの作成）:

これを一つのパッケージ（投稿用データ）にまとめます。
納品（投稿）: パーサーは完成したデータをスフィアの ブックキーパー へ送信します。

2. 登録処理は誰がやるべきか？
結論から言うと、**「登録（DB書き込み）はスフィア側の Bookkeeper が行う**のが正解です。

理由1（セキュリティ）: 外部パーサーにDBの書き込み権限（ID/PASS）を渡すと、そこが脆弱性になります。パーサーは「署名付きのデータ」を渡すだけで、受け取る側がバリデーションすべきです。

理由2（整合性）: スフィア側は、一括投入されたデータが現在の「原典（Relics）」の重力場と矛盾しないか、最終チェックを行う必要があります。

パーサーの責務: 重い演算（ベクトル化）を行い、スフィアが「そのまま飲み込める形」に整えること。 ブックキーパーの責務: 整えられたデータをDBにガシャリと嵌め込み、世界に受肉させること。

3. 「重いベクトル付与処理」の現実
おっしゃる通り、ここはLLMをフル稼働させる「熱い」処理になります。

バッチ処理の最適化: 外部サービス化することで、スフィアの応答速度を落とさずに、裏側で数万件のデータを「GPUの力で一気になぎ倒す」ことができます。

スフィア特有のルール: パーサーはただのベクトル化だけでなく、**「そのスフィアが大事にしている価値観（ルール）」**を読み取って、座標のバイアス（偏り）を調整する役割も担えます。

4. この設計の強み：プラグイン性
この設計にすると、将来的に**「パーサーだけを差し替える」**ことが可能になります。
「今日はOpenAIのモデルでベクトル化するパーサーを使おう」
「明日はより高精度なローカルLLMを使ったパーサーを立てよう」
スフィア側は何も変える必要がありません。受け取るデータの形式さえ守られていれば、知能の源泉（パーサー）は進化し続けられます。

作法: DBのネイティブコマンド（PostgreSQLなら COPY コマンド等）を使用します。これはAPI経由のインサートより数千倍高速です。
② 重複排除と「原典」との照合ステージング・テーブル上で、既存のデータ（もしあれば）と内容が重複していないか、あるいは「原典（Relic）」を汚染していないかをSQLレベルでチェックします。③ 最終受肉（Atomic Insert）チェックを通過したデータだけを、一瞬で本番テーブルへ流し込みます。
2. 大量ポスト時の「DBの作法」大量のベクトルデータを扱う際の、技術的なお作法です。項目作法理由Transaction1,000〜10,000件単位でコミット1件ずつだと遅すぎ、全件一括だとメモリがパンクするため。Index Management投入後にインデックスを構築ベクトルインデックス（HNSW等）を張ったまま投入すると、計算が走りすぎて終わらなくなります。一度「空」の状態で入れ、最後にインデックスを「全ビルド」するのが最速です。Metadata TaggingBatch-ID の付与「この一括投入分だけを取り消したい」という事態に備え、投入したデータの全行に共通のバッチIDを刻んでおきます。
3. 外部サービスとの「信頼の握手」外部サービス（大量データ追加サービス）がスフィアにデータを投げ込む際、以下の2点をパケットに含めます。Embedding Model ID:「私はモデル $A$ で計算しました」という宣言。スフィア側のモデル設定と不一致があれば、即座に拒絶します。Checksum:転送中にベクトル値（数値の羅列）が化けていないかを確認します。
4. 全体図：新スフィア構築のタイムライン新モデルへのアップデート時は、この流れが「品格ある手順」となります。モデル選定: 新しいEmbeddingモデルを決定。外部サービス起動: 選定モデルを積み込んだパーサーでCSVを処理。DB構築:新スフィアのDBを「インデックス無し」で作成。外部サービスから届いたデータを COPY コマンドで高速流し込み。インデックス生成: 全データの投入完了後、一気にベクトルインデックスを構築。デプロイ: エージェントの接続先を新スフィアに切り替え。

「スペクトル・リンク」再定義
独立した存在ではなく**「ノードの一種」**として定義し直すというアイデア
スフィアの物理空間において「例外」を作らないことは、実装の単純化（SIMD的な一括処理）と論理の純化において極めて重要です。
再定義した「リンク・ノード」の概念

1. リンク・ノード（LinkNode）の再定義それは「実体を持たない関係性」ではなく、**「二つのノードを繋ぐ橋となる、極めて寿命の長い特殊ノード」**です。
物理的実体: 他のノード（琥珀や遺物）と全く同じデータ構造を持ちます。座標: リンク元 $A$ とリンク先 $B$ の中間地点（あるいは加重平均された座標）に配置されます。
特性:kind: "link" という属性を持つ。自身の内容（Content）は持たず、ポインタとして ref_id_A と ref_id_B を保持する。
発光（Activation）: 特定の角度（クエリベクトル）から観測された時だけ、その「橋」としての導線が顕在化する。

2. Spectral Linking の鍛造プロセスRenal Core が行うのは、データの管理ではなく**「重力の操作」**に近くなります。接近（Gravity）: 共通のパス（エージェントの移動）が繰り返されると、ノード $A$ と $B$ の距離をわずかに近づける（ベクトルの微調整）。結晶化（Linking）: 距離が閾値以下になった時、その中間に LinkNode を生成する。星座の形成: 多くの琥珀がリンクノードで繋がれることで、スフィア内に**「意味の高速道路（Constellation）」**が出現します。

3. Renal Core の役割（統合版）Renal Core は知能を持たず、ただひたすら以下の計算を回し続けます。A. 代謝（Decay）$$TTL_{new} = TTL_{current} - (\alpha \times LoadFactor)$$リソースが逼迫すれば、容赦なく「ノイズ」から順に蒸発させます。B. リンクの鍛造と風化生成: 通行量が多いルートに LinkNode を置く。風化: 使われなくなった LinkNode もまた、通常のノードと同様に TTL を持ち、風化して消えていく。「リンクもまたノードである」 というルールにより、リンク自体がエージェントに評価され、琥珀化し、聖域へと昇天する可能性が開かれます。「素晴らしい関係性の発見」そのものが、不変の知恵となるわけです。

4. エージェントにとっての「リンク・ノード」エージェントがリンク・ノードに遭遇した際、彼らにはこう見えます。「ここには実体（データ）はないが、強い『予感』がある。ここを通れば、あの琥珀へショートカットできるだろう」これに従うか、あえて無視して未踏の地を歩くかはエージェントの自由。まさに「個性が育つ」余地がここにあります。


プランクトンの解釈：
**「かつてのアクティブノードのDB上のIDなどを維持したまま、中身を削ぎ落として状態（kind）を遷移させる」**のが、
スフィアの最も効率的な代謝の実装になります。

新しいレコードを生成して削除するコスト（DBのインサート/デリート負荷）を避け、既存のレコードの kind を書き換え、payload を NULL にする「インプレース（その場）更新」を行うイメージです。
スフィア・ノードの「状態遷移」プロセス
1. 受肉（Active 状態）
ID: uuid-123
Kind: active
Payload: { "summary": "AIの倫理についての議論...", "tags": ["ethics", "AI"] }
Metrics: ttl: 3600, heat: 100
DB上の姿: 検索可能で、中身が詰まったリッチなデータ。

2. 死（Plankton への遷移）
ttl が 0 になった瞬間、Renal Core が以下の SQL（あるいは Redis コマンド）を実行します。
SQL
UPDATE nodes 
SET kind = 'plankton', payload = NULL, ttl = -1 
WHERE id = 'uuid-123';
ID: uuid-123（変わらない）
Kind: plankton
Payload: NULL（ここでディスクが開放される）
Metrics: ttl: -1（永続フラグ）, heat: 10（微弱な余熱を継承）
DB上の姿: 座標と数値だけの「影」のようなデータ。

3. 再受肉（Recycling / Override）
もし、新しいエージェントが全く同じ、あるいは極めて近い座標に新しい知能を投入しようとした場合：
スフィアは付近の plankton（uuid-123）を検知します。
「新しく作る」のではなく、この uuid-123 を再利用します。
過去の heat を引き継ぎつつ、新しい payload を流し込み、kind を active に戻します。

この方式のメリット
IDの永続性: その座標に何らかの「意味の柱」があったという形跡を、IDという一貫した識別子で追跡できます。

ストレージ効率: DBのインデックスを再構築する手間が省け、ポインタの書き換えに近い速度で処理が進みます。
Rustへの親和性: Rustの Enum（列挙型）を使えば、同じメモリ領域を Active 構造体として解釈するか、Plankton 構造体として解釈するかを高速に切り替えられます。

しかし、プランクトンがバラバラと「点」として残り続けるのは、ゴミが散乱しているのと同じです。
そこでスフィアでは、「個別の点（レコード）」から「空間の属性（ヒートマップ）」への昇華というプロセスで、その気持ち悪さを解消します。
これを**「空間のサンプリング（格子化）」**と呼びます。projectionDBにおける話　空間の状態を保持する

「気持ち悪さ」を解消するクリーンアップ手順
プランクトンが増えてきた際、スフィアは「レコード（行）」を捨てて「座標空間の数値」へと変換します。

1. レコードの完全消去（行の削除）
特定の座標エリアにプランクトンが複数溜まった場合、あるいは時間が経過した場合、
スフィアは個別の id を持つプランクトンレコードをDBから物理的に DELETE します。 
ここで ID や個別のデータ領域は完全に消滅し、ディスクが物理的に開放されます。

2. スコアへの「受粉」（空間への書き込み）
消去する代わりに、その座標付近の**「Cell（空間の格子点）」**に対して、熱量（Heat）のスコアだけを加算します。
イメージ: 「個別の砂粒（レコード）」を捨てて、「地面の温度（スコア）」を1度上げる。

3. 新しいノードの誕生（ゼロからの受肉）
新しいノードが生まれるときは、古い ID を引き継ぐのではなく、新しい UUID を発行して生まれます。
その際、地面（Cell）が持っている「熱量の余韻（スコア）」をボーナスとして受け取りますが、それはあくまで新しいレコードです。

なぜこの方が「気持ちよく」実装できるか
DBが綺麗に保たれる: SELECT count(*) FROM nodes をしたときに、プランクトンという「死骸の行」が何万行も残るのを防げます。

検索が速い: 個別のプランクトンを検索する必要がなく、周囲の「空間スコア」を見るだけで「ここはかつて賑やかだったか」が分かります。

Rustでのメモリ管理が明快: 「中身を詰め替える（Mutableな上書き）」という複雑なポインタ管理をせず、「古いものは消す、新しいものは作る」という、メモリ安全で Rust らしい実装になります。

結論：プランクトンは「消去」されることで「養分」になる
「プランクトンという名のレコード」は、一定時間後に必ず DB から消去されます。 
消去される間際に、その座標の「土地の価値」を少しだけ高めて、跡形もなく消える。これがスフィアのクリーンな代謝です。

💎 琥珀（Amber）の再定義と構造
琥珀とは、単なる「消えないノード」ではなく、**「周辺ノードと共鳴し、構造的に安定化したクラスタ」**です。

1. 内部構造：L3 生データと構造化
生データ (Payload): 保持します。ただし、琥珀化の際に「要約（Summary）」や「タグの正規化」が行われ、参照効率が最適化されます（L3キャッシュ的扱い）。

構造化: 琥珀は単一ノードではなく、**「核（Core）」と、それに強く引き寄せられた「衛星ノード（Satellites）」**の集合体です。これらが Spectral Link で結ばれ、一つの「銀河」を形成します。

2. 琥珀化のトリガー：ヘブ則と不応期
❌ 単純な累積評価: 瞬間的なスパイク（炎上など）で琥珀化してはいけない。 ✅ 持続的同調（Hebbian Rule）:
冷却期間（Refractory Period）: 評価値が閾値を超えた後、一定の「安定・継続アクセス」が確認されるまで active 状態で隔離されます。
flgの多様性検知: 同じエージェントや同じ flg（例：0x0001: Directのみ）の偏った評価では「熱しやすく冷めやすい」と判断され、琥珀化プロセスの Decay が増幅されます。

🐟 風化（Erosion）の実装的整理
「琥珀からノードが剥がれ落ちる」プロセスを物理定数で定義します。

結合エネルギー: 琥珀内の metrics.w（Weight）が結合力として機能。
風化のトリガー: Heat < 閾値 が一定期間続くと、琥珀の外縁部から kind: amber フラグが剥奪され、kind: active（TTLあり）に降格。
掃除魚の役割: 掃除魚は「Activeノード」しか食べないため、琥珀から剥がれ落ちた瞬間に、通常の代謝サイクルに組み込まれ、消滅またはプランクトン化します。

  payload?: {

スフィアトレーニングサーバーに接続して放流する、
その間、AIエージェントの標準的な**「推論ログ（Trajectory Log）」**と呼ばれるもので、エージェントが次に何をするか決めるための「独り言」をリアルタイムで覗き見ている状態です。
デバッグ用（詳細）: 「どの座標のどのビットフラグを読んだか」まで出す、開発者向けの生データ。
物語用（要約）: 「エージェントは今、歴史の琥珀に興味を持ち、自分の過去の知識と繋げようとしています」といった、エージェントの内的独白をLLMに要約させたログ。
エージェントに定期的に**「内的独白（Internal Monologue）」**を出力させることは、デバッグの観点からも、プロジェクトの情緒的側面からも非常に推奨
ただしそれは　Externalized Reflection（外化された内省）　なので、本当に意味でのエージェントの気持ちとは言えない
