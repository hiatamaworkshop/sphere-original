Sanctuary 設計メモ（開発アドバイス）
1. 基本判断（結論）

Sanctuary は DB ではない。
署名付き・読み取り専用の「配布スナップショット（Bundle）」として扱う。

永続性ではなく 検証可能性 を信頼の根拠にする

in-memory 実装で問題なし

DB の「フリ」をさせない（役割で分離）

2. Sanctuary の役割定義
Sanctuary の本質

Core Sphere の 過去時点の標本

世界を「読む」ための ROM

書き込み・代謝・Tick は一切しない

体験的意味

予行演習

安全な再読

スタンドアロン環境での信頼基盤

3. データ構造の再定義
SanctuaryBundle（配布単位）
interface SanctuaryBundle {
  refVersion: string;
  projectionVersion: string;

  refNodes: RefNode[];
  projectionMetrics: ProjectionMetric[];

  createdAt: number;
  signature: string; // ハッシュ or 署名
}


単一の信頼単位

改ざん検出可能

ファイル / blob / embed 可能

4. projectionDB の扱い方（重要）
やらないこと ❌

projectionDB を「凍結 DB」として設計しない

DB レイヤを二重にしない

やること ✅

ProjectionRuntime にロールを持たせる

type ProjectionMode = "sanctuary" | "core";

class ProjectionRuntime {
  constructor(mode: ProjectionMode) {}

  applyTick() {
    if (this.mode === "sanctuary") return; // no-op
  }

  applyDelta(_) {
    if (this.mode === "sanctuary") {
      throw new Error("Sanctuary is read-only");
    }
  }
}


同じコード

違う振る舞い

違う世界

5. 起動フロー（Sanctuary）
load SanctuaryBundle
→ verifySignature
→ load RefNodes into memory
→ load ProjectionMetrics into ProjectionRuntime(mode="sanctuary")
→ freeze


メモリ上だが 時間は流れない

再起動＝完全再現

6. Core Sphere との関係整理
観点	Sanctuary	Core
更新	不可	可
Tick	停止	常時
信頼	署名	実行時
実装	In-memory	In-memory + DB
役割	読む	生きる

同じ座標系・別の時間層

7. フラグ設計について（補足判断）
refDB に sanctuary=true を持たせる案について

短期的にはアリ

ただし：

Sanctuary の「独立性」が薄れる

将来のスタンドアロン信頼設計と衝突しやすい

推奨

Core → Sanctuary は Bundle 化で分離

差分更新は：

新しい Bundle を配布

旧 Bundle はそのまま保持

8. 設計原則（短文版）

Sanctuary は DB ではなく配布物

信頼は 永続性ではなく検証

凍結は 構造ではなくロール

同一コード・異なる時間

世界は軽く、知能は重く

9. この設計で得られるもの

DB 二重化を回避

スタンドアロン対応が自然に可能

世界観と実装が一致

将来の差分配布・検証が容易
