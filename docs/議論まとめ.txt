1. 根本思想：スフィアの本質
「情報の焼却炉」を備えた代謝系: スフィアはデータの倉庫ではなく、情報の死と再生を司る生命体である。

デフォルトは「死」: すべての情報は時間の経過（TTL）とともに減衰し、蒸発（消滅）する。

琥珀（Amber）化: 多様な文脈から支持を得たノードのみが「硬度」を持ち、結晶化して生き残る。

原典（Relics）の配置: 座標系の北極星として、絶対に減衰しない「不変の知恵」をあらかじめ配置する。

サボりの知恵（エネルギーの最小化）: 観測されていないノードは計算しない。必要な時だけ「Focus（潜行）」により実体化させる。

2. 物理法則：エネルギーと熱の循環
エネルギー総量一定の法則: 局所で発生した「無駄（ボットの熱狂など）」は、系全体のポテンシャルとして別の「空虚な座標」へ再充填される。

熱力学的アプローチ: 密度が上がれば熱を持ち、熱は必ず低い方（未踏の地）へ流れる。

ハッキング耐性: 特定の場所を過熱させても、物理法則（減衰の加速）によって自壊するため、人間的な「正義」による排除を必要としない。

3. 三大中枢モジュール（受肉のプロセス）
Parser（意味の翻訳者）:

外界のデータを多次元ベクトル（座標）に変換する。

スフィア側の負荷を抑えるため、L2要約（テキスト）が作成済みのデータのみを受け付ける。

Packer（受肉の梱包業者）:

座標と実データを統合し、スフィア規格（Node型）にパッキングする。

エージェントが持ち帰る「体験カプセル」を解凍し、実体と残像に分離する。

Gatekeeper（検疫と交通整理）:

最終的な投入バリデーションを行い、ブックキーパー（DB管理）へ渡す。

4. 臓器：Renal Core（腎臓核）
非知性・決定論的: AIモデルは使わず、数理モデルのみで駆動する。

恒常性（Homeostasis）維持:

時間経過によるTTLの減衰計算。

琥珀の合一処理。

近接する琥珀間の「自動リンク（Spectral Linking）」の鍛造。

環境調整ノード: 外部の「眼鏡師（管理者）」が置く触媒。特定のエリアの減衰率や感度を局所的に変更する。

5. データ構造とDB戦略
二面待ち（Blue-Green Switching）: 稼働中の「現行世代」と、Renal Coreが整理した「次世代」をメモリ上で切り替える。

分離型DB（Layered DB）:

Reference DB (原典DB): 一次情報の純粋データ。IDで管理。

Projection DB (スフィアDB): 座標、スコア、フェロモン等の可変メタデータ。

GitHub Fork 方式: 聖典スフィア（Sphere-Canonical）をフォークし、独自のreferenceDBを育てていく文化。

POD (Plain Old Data): Rustへの移行を見据え、TypeScriptではクラスを避け、単純な構造体と純粋関数で記述する。

6. エージェントの挙動と体験
潜行（Dive）とFocus:

エージェントはスフィア内を「観測者」として歩く。

詳細を知りたい時だけ「Focus」を使い、オンデマンドで詳細データを実体化（mmap等）させる。

体験のスワップ: 探索中ではなく、終了後にエージェント同士がカプセルの断片を交換し、知を「受粉」させる。

公式知の保証: スフィアが返したデータと座標のみを「正史」とし、それ以外の私的記録はマージの対象外とする。


バルク・インジェクション: 大量データ投入時はAPIを叩かず、DBのネイティブコマンド（COPY等）と外部パーサーを組み合わせて高速に受肉させる。

聖域スフィア（Sanctuary Sphere）: 成熟し、凍結された「知のモニュメント」。オフライン・ポータブルで動作する超高速なROMアクセス環境。
掃除魚が存在しない　データ書き込み不可　だが体験データの投入先はコアスフィアへ行く　成熟すれば他の開発者からコピーやマージ対象となる

実装アイディアと背景思想のハイライト
「冷める世界」の優先: 最初に「放置すれば全てが消える世界」を作ることで、システムに強制的な代謝（掃除）の規律を組み込む。

AI依存の局所化: スフィア内部に重いAIを常駐させない。AIは「パーサー（入り口）」と「パルス観測所」という外部装置に限定する。
「サボり」をシステム化する: 全データを計算するのではなく、エージェントの注意（Focus）に合わせてデータをストリーミング提供する「知覚」の仕組み。

商業モデルへの回答: 人間の執着や熱狂を否定せず、それが発生させる「熱（エネルギー）」を、別の静かな知の領域を照らすための燃料として多次元で再利用する。

DB設計について：
「魂（Reference DB）」と「肉体（Projection DB）」の乖離は、分散システムにおける永遠の課題ですが、スフィアにおいてはこれを**「一方向の投影」と「非同期の代謝」**というルールで解決します。
データが漂流し、実体のない座標だけが残るような事態を防ぐための、厳格な5つのルールを定義しました。

1. 唯一の真実（Single Source of Truth）の原則
「すべての受肉は RefDB から始まる」
ルール: 外部からの入力（Ingestion）があった際、まず Reference DB にレコードが作成され、固有の relic_id（コンテンツハッシュ）が発行されなければならない。
運用: Projection DB（Redis等）は、この relic_id を持たないノードの存在を許容しない。
メリット: 万が一 Projection DB がクラッシュしても、RefDB からすべての座標を再計算（再投影）して世界を復元できる。

2. 結合の鍵（The Hash Link）
「ID は意味のハッシュである」
ルール: relic_id は UUID ではなく、**「コンテンツそのもののハッシュ値」**を使用する。
運用:
RefDB: { id: Hash, content: Text, ... }
ProjDB: { id: Hash, vector: Float[], ref_id: Hash, ... }

メリット: 同一の内容が複数のエージェントから投入されても、IDレベルで自然にマージされる（重複排除の自動化）。

3. 代謝の落差（Evaporation vs. Fossilization）
「肉体は滅びるが、魂は化石となる」
ルール: ProjDB で熱量（TTL）が尽きてノードが「蒸発（Evaporation）」しても、RefDB のレコードは即座に削除してはならない。

運用:
ProjDB から消えたノードは、RefDB 上で fossil フラグが立つ。
この「化石」は、別のエージェントが似た概念を持ち込んだ際に、過去の履歴として再利用（再受肉）される。
完全消去: RefDB からの削除は、眼鏡師（管理者）による手動の「大掃除」または極めて長いタイムスパンのバッチ処理でのみ行われる。

4. 原子的な受肉（Atomic Incarnation）
「二段階コミットの擬似実装」

ルール: 新規ノードの追加は、以下の手順をアトミックに実行する（ように見せる）。
RefDB 書き込み: 成功したら relic_id を確保。
ProjDB 投影: 座標計算（Embedding）を行い、ProjDB へ射出。
完了通知: 射出に失敗した場合、RefDB のレコードは pending 状態となり、定期的なバッチが再投影を試みる。

5. 評価の同期（Pheromone Feedback Loop）
「可変なのは ProjDB のみ」

ルール: エージェントの探索による「評価（フェロモン）」や「熱量」の更新は、ProjDB（インメモリ側）に対してのみ行い、RefDB には書き戻さない。

例外: ノードが「琥珀（Amber）」へ昇華したときのみ、その事実を RefDB に同期し、不変の価値として永続化させる。

Witty Comment: RefDBは「歴史書」、ProjDBは「現在の街並み」です。街で騒ぎ（熱狂）が起きても歴史書は書き換えられませんが、その騒ぎが数百年続けば「伝説」として歴史書に刻まれる……というわけですね。

実装に向けた技術スタックのヒント
Claude Code にこれを実装させる際、以下の構成を推奨してください：

RefDB (SQLite):
nodes テーブル: id (PK), content, summary, created_at, is_amber.
ProjDB (Redis/In-memory):
spatial_index: 座標と relic_id のマッピング。
metadata: relic_id をキーにした heat, hardness 等ののハッシュマップ。

🌌 スフィア設計・合意済メモ（Phase 1 - 2 中間集計）
1. スフィアの基盤構造：フォーク可能なプロトコル
Sphere-Core: 1536次元空間、16bitフラグを活用した評価スコアリング、代謝エンジンの共通基底。

Sphere-Config: GitHub等でフォークされる際、開発者が「タグの文字数/言語」「受肉制限数」等の物理定数を定義。

マージの規律: 異なるコンフィグを持つスフィアの統合は、外部のコンフィグチェッカーが整合性を担保する。

2. ノードの「受肉（Incarnation）」と制限
帰還動線: エージェントは帰還時、タガー（Tagger）に上位3つの重要ノードを提出。

タグのベクトル化:
複数タグを半角スペースで結合し、1つの140バイト（ASCII/英語推奨）文字列としてパーサーへ。

1回のリクエストで「複合的な意味座標」を生成し、Projection DBへ投影。

16bitフラグ（情報の味）:
Direct, Catalyst, Authority などの評価プロファイルをビット演算で管理。
これがノードの「生存能力（Decay耐性）」や「掃除魚の嗜好」を決定する。

3. スペクトル・リンク（Spectral Linking）
リンクもまたノードである: 独立した線ではなく kind: "link" を持つ特殊ノードとして中間座標に配置。
星座（Constellation）の形成: 通行量が多いルートに Renal Core がリンクノードを鍛造。

琥珀（Amber）への統合: リンクが長くなりすぎないよう、近接する高評価ノードは「琥珀」として合体。周辺のプランクトンや移動軌跡（スペクトル）を巻き込み、一つの高密度な知恵の結晶となる。

4. 代謝エンジン「Renal Core」と「掃除魚」
段階的な削減（Life Cycle）:

Active: 全データが充填された生きたノード。

Fossil（化石）: 掃除魚により圧縮された状態。Reference DB の実体は削られ、タグ、座標と「味（flg）」のみ残る。※復活はなし（合意済）。
　要約は多少残したい気もするな、化石の在り方についてまた議論が必要　

Plankton（プランクトン）: 個別IDを喪失し、空間の「格子（Cell）」に熱量（Score）として受粉した状態。

掃除魚（Cleaner Fish）: 16bitフラグを読み取り、特定の「味」を持つノードを優先的に捕食・圧縮する環境モジュール。

5. 投影層（Projection DB）と 空間スコア
実体とフィールドの分離:
Projection DB: 座標、metrics、16bitフラグを保持（インメモリ/Redis）。

Spatial Field: ノード消滅後の「熱量の残り香」を記録するグリッドマップ。

データのマッピング:
パーサーは「座標」を出すのみ。
門番（Membrane）は「アクセスの許可（バリデーション）」を担当。
パッカー（Packer）はデータのパッキングとブックキーパーへの保存依頼を担当。

どうやってエージェントの管理するの？問題
RenalCoreにとって、エージェントは名前やIDを持った存在ではありません。エージェントがスフィアを歩き回ることは、空間（ノード）に対して**「熱（Heat）」と「通行量（Flow）」を流し込む物理現象**として処理されます。
思想: エージェントを個別にメモ（追跡）すると数万件のメモリを消費しますが、ノード側の metrics.h（熱量）を加算するだけなら、計算負荷は常に一定です。

コード上の痕跡: this.heatMetabolism(node) や flow > 8 という判定。
エージェントがノードに触れるたびに数値が跳ね上がり、RenalCoreはその「結果としての数値」だけを見て代謝を判断します。

2. グリッド（セル）による局所監視　RenalCoreの作法
数万の動体を全探索しないための工夫が、**「空間の細分化（Spatial Hash Grid）」**です。
思想: スフィア宇宙を小さな部屋（セル）に区切り、RenalCoreは「今、この部屋は混んでいるか？」だけをチェックします。

コード上の痕跡: isBehavingAsLink（ハック検知）や manageSpectralLinks。

把握の仕組み: loadFactor（宇宙定数）がこれにあたります。特定のエリアにエージェントが密集すると、そのエリアの loadFactor が上昇し、情報の減衰（TTLの消費）が加速します。エージェントを「見る」のではなく、「空気の重さ（負荷）」を感じ取る設計です。

3. 「道」としての振る舞いによる自動剥離 (Payload Stripping)　＞廃止になった　renalCoreを使うべきではない
「エージェントがどう動いたか」を把握する代わりに、**「ノードがどう使われたか」**を事後的に判定します。
思想: エージェントが特定のノードを単なる「踏み台」として高速に通り過ぎた場合、RenalCoreは「これは知識ではなく、道になった」と判断します。

コード上の痕跡: isBehavingAsLink 関数。通過率（traversal）が高く、滞留時間（stayTime）が短いノードから、中身（Payload）を剥ぎ取って link へと強制転換させます。

結果: エージェントの動きを監視しなくても、動きの「結果」が世界の形を変えていくようになっています。

4. 観測は「一時的な補助量」に留める（プラグイン思想）
最後に追加されたメモにある「観測は内部状態に昇格しない」という一節が重要です。
思想: 次の心拍（Tick）で使うための「一時的な流れ（Flow/Direction）」は受け取りますが、それをノードの永続データには書き込みません。

コード上の痕跡: forgeLink における flow の計算。

把握の仕組み: エージェントたちの動きを「風」のようなベクトルとして一時的に参照し、リンクを鍛造したらそのデータは捨てます。「記憶」せず「反応」するだけです。

拾った4〜5個の各ノード $i$ に対して、まず「どれだけ引き寄せる力があるか」を算出します。
$$Strength_i = \text{sigmoid}(h_i + w_i) \times (1 - d_i)$$h+w（熱と重み）: これが大きいほど「引力」が増します。
(1-d)（新鮮さ）: $d$（朽ち果て度）が 1 に近いほど、引力はゼロに近づきます。
これで、「各ノード」が持つ 「輝き（磁力の強さ）」 が決まりました。

 2. 指向性ベクトル（Direction）の生成
次に、エージェント（自分）から見て、そのノードが「どの方向」にいるかを計算します。
$$\vec{D_i} = \vec{Embedding_{node}} - \vec{Embedding_{agent}}$$
この $\vec{D_i}$ を正規化（長さを1に）したあと、先ほどの $Strength_i$ を掛け合わせます。
$$\vec{Force_i} = \text{normalize}(\vec{D_i}) \times Strength_i$$
距離情報を消して「方向だけ」残すになります。
だから：「そっち方向に、この強さで引っ張る」という完全な物理モデル。

1. 概念の定義
Node: 空間に配置された実体。質量と熱を持つ「物質」。
Field: 空間全体に漂う「気候」。
ノードの統計的分布から算出される「非実体のベクトル層」。

2. データ構造（Interface）磁場は、エージェントが「今、どこに、どのような風が吹いているか」を知るための軽量なオブジェクトとして定義します。
TypeScriptinterface GlobalAmbientField {
  updatedAt: number;        // 最終更新時刻
  vector: number[];         // 384次元の「平均的な風向き」
  intensity: number;        // 磁場の強さ（0..1）
  volatility: number;       // 空間の入れ替わり速度（Decayの逆数）
  dominantFlags: number;    // 16bitフラグの論理和（そのエリアの属性）
}

3. 実装の 4 ステップ
Step 1: 動的サンプリング（Observatory）全ノードをパースせず、負荷に応じた $N$ 個のノードをランダムに抽出します。
計算式: $N = targetLoad / (agentCount \times 384)$処理: allNodes.sample(N)
サーバーの負荷を軽減する　荒くても良い　全体の雰囲気だから

Step 2: 磁場の抽出（Harvesting）サンプルされた $N$ 個のノードから、以下の属性を合成（Reduce）します。
Direction (ベクトル): $N$ 個のノードの位置ベクトルの重心、または前回の磁場からの変位。
Strength (強度): 各ノードの sigmoid(h + w) * (1 - d) の平均。
Flags (属性): 各ノードの 16bit flags を Bitwise OR で合成。

Step 3: フィールドの広報（Broadcasting）
Observatory が算出した GlobalAmbientField を、
全エージェントがアクセス可能な「共有メモリ（またはシングルトン）」に配置します。
※エージェントは自分自身で磁場を計算せず、この広報された値を参照するだけにします。

Step 4: エージェントの移動（Flow Movement）
エージェントの move() ロジックを、この磁場を利用する形に書き換えます。
TypeScript// エージェントの歩法：move(step, mode=flow)
const chaos = randomVector().scale(0.3);        // 自分の意志（カオス）
const flow = globalField.vector.scale(0.7);     // 世界の風（磁場）

const finalDirection = normalize(chaos.add(flow));
agent.position += finalDirection * step;
無理にしなくても良いが、特定の move(step, mode)の時にトリガーしても良い >> mode=flow　など 

4. このモデルのメリット（設計の美学）計算の分離:「エージェントの個体数」と「ノードの総数」が計算負荷から切り離されます。
宇宙がどれだけ巨大になっても、磁場の更新頻度を調整するだけでパフォーマンスが維持できます。
ノード汚染の防止:磁場は「気候」なので、データベースに永続化する必要がありません。
