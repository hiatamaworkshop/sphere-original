## 1. Embedding Model 決定

### 選定結果

| 項目 | 決定 |
|-----|------|
| モデル系列 | Sentence-BERT (MiniLM / MPNet) |
| 次元 | 384〜768 |
| ランタイム | `@xenova/transformers` |

### 第一候補

| モデル | 次元 | 用途 |
|-------|-----|------|
| `all-MiniLM-L6-v2` | 384 | 最軽量・高速 |
| `all-mpnet-base-v2` | 768 | 高品質・バランス |
| `paraphrase-multilingual-MiniLM-L12-v2` | 384 | 多言語対応 |

### 選定理由

- 意味距離が素直でデバッグしやすい
- 差分ベクトルが安定（spectral link 判定に有利）
- Redis/In-memory に優しいサイズ

> 方針: まずこれで「迷路の形」を作る

## 2. Parser の役割確認

### パイプラインフロー

```
Agent Request
    │
    ▼
Membrane (Physical Check)
    │ 禁止パターン除去、正規化
    ▼
Gatekeeper (Structural Validation)
    │ ノード数、サイズ、heat範囲
    ▼
Tagger (Vectorization)
    │ tags → vector (topTierのみ)
    ▼
Packer → Bookkeeper → SphereNode
```

### 重要な確認事項

- リクエストは直接座標モデルに入らない
- `tags` が vectorize される（summary ではない）
- Membrane は物理チェックのみ（意味解釈なし）

## 3. NodeSeed データ構造の明確化

### 問題

- `summary` フィールドの役割が曖昧だった
- 「エージェントの問い」と「発見物」の混同

### 解決

| フィールド | 役割 | 説明 |
|-----------|------|------|
| `tags` | COORDINATES | 発見物の空間位置（多いほど精密） |
| `summary` | HEADLINE | 発見物の見出し（遠くから見える） |
| `payload` | DETAILS | 発見物の詳細（近づいて読む） |

### 哲学

> "You enter as a seeker, you return as a giver."
> 探索者として入り、贈与者として帰る。

- Agent の mission（問い）は Capsule に入れない
- Capsule には「発見物（答え）」のみを格納
- mission は Agent の内的動機として保持

## 5. Parser & Tagger 責務分離

### 重要な設計決定

| コンポーネント | タイミング | 用途 |
|--------------|-----------|------|
| **Parser** | 探索前 | Agent の初期位置 + Quest ベクトル決定 |
| **Tagger** | 帰還時 | 発見物のノード座標決定 |

### Request と Quest の分離

**重要**: Request と Quest は異なる座標を持つ可能性が高い。

| 項目 | 由来 | 用途 |
|-----|------|------|
| `initialPosition` | Request | spawn 位置（どこから出発） |
| `questVector` | Quest | 探索目標（どこへ向かう） |

```
例:
  Request: "データベースについて調べたい"     → 広い領域
  Quest:   "PostgreSQL JSONB パフォーマンス" → 狭い特定領域
```

### Entry Flow

```
クエスト閲覧 → 受諾決定 → パーサー → 琥珀ショーケース → チュートリアル世界
                           │
                           ├── embedBatch([request, quest])
                           │       ↓
                           └── [initialPosition, questVector]
```

**効率**: バッチ処理により1回の呼び出しで両ベクトル取得

### 共通インフラ

- `embedding/` ディレクトリに共通の EmbeddingProvider
- Parser と Tagger は同じモデルを共有
- **ローカルモデルのみ使用可**（API 禁止）

## 6. Embedding Model 制約

### API ベース禁止

| 禁止 | 許可 |
|-----|------|
| OpenAI text-embedding-* | @xenova/transformers |
| Cohere embed-v3 | ort (ONNX Runtime) |
| Voyage AI | Rust ort（将来） |

**理由**: 人間世界の資源を無駄にしない。Sphere は自己完結したエコシステム。

### 推奨モデル

| モデル | 次元 | 用途 | メモリ |
|-------|-----|------|--------|
| `all-MiniLM-L6-v2` | 384 | **第一候補** - 最軽量・高速 | ~50MB |
| `all-mpnet-base-v2` | 768 | 高品質・バランス | ~250MB |
| `paraphrase-multilingual-MiniLM-L12-v2` | 384 | 多言語対応 | ~100MB |

### スケーリング指標

| 指標 | 384次元 | 768次元 | 備考 |
|-----|---------|---------|------|
| ベクトルサイズ | 1.5 KB | 3 KB | Float32 |
| 100万ノード | 1.5 GB | 3 GB | Redis メモリ |
| embedBatch(10) | 50-200ms | 100-400ms | CPU |
| embedBatch(10) | 10-50ms | 20-100ms | GPU |

### スケールアップ時の切り替え判断

```
Phase 1: all-MiniLM-L6-v2 (384次元)
  └── ノード数 < 100万、標準用途

Phase 2: paraphrase-multilingual-MiniLM-L12-v2 (384次元)
  └── 多言語コンテンツ増加時

Phase 3: all-mpnet-base-v2 (768次元)
  └── 検索精度が課題になった場合
  └── メモリ 2倍、次元数変更で既存データ非互換
```

### デプロイ時の柔軟性

開発者の環境・リソースに応じて、より高次元のモデルも選択可能。

| 環境 | 推奨次元 | モデル例 |
|-----|---------|---------|
| 軽量環境（推奨デフォルト） | 384 | all-MiniLM-L6-v2 |
| 標準環境 | 768 | all-mpnet-base-v2 |
| 高性能環境 | 1024+ | e5-large, BGE-large |

```
┌─────────────────────────────────────────────────────────────────┐
│  次元数は設定で変更可能                                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  sphere.config.json:                                             │
│  {                                                               │
│    "embedding": {                                                │
│      "modelId": "Xenova/bge-large-en-v1.5",                     │
│      "vectorDimension": 1024                                     │
│    }                                                             │
│  }                                                               │
│                                                                  │
│  制約:                                                           │
│    - ローカル実行可能なモデルのみ（API 禁止）                    │
│    - 次元数変更時は既存データと非互換                            │
│    - メモリ・ストレージ要件を考慮                                │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 9. 本日の決定事項まとめ

### 原則

| 原則 | 内容 |
|-----|------|
| **API 禁止** | Embedding は必ずローカル実行。人間世界の資源を無駄にしない |
| **言語中立** | Sphere は特定の国・言語を優遇しない |
| **自己完結** | 外部依存を最小化。Sphere は独立したエコシステム |

### アーキテクチャ決定

| 項目 | 決定 |
|-----|------|
| Parser タイミング | 探索前（Dive Entry） |
| Tagger タイミング | 帰還時（Incarnation Pipeline） |
| Request/Quest | 別座標として扱う（バッチ処理で効率化） |
| Embedding Model | Sentence-BERT (MiniLM/MPNet) |
| デフォルト次元 | 384（デプロイ時に変更可能） |

### データ構造

```
NodeSeed:
  tags     → COORDINATES (空間位置)
  summary  → HEADLINE (見出し)
  payload  → DETAILS (詳細)

AgentSession:
  request         → 原文
  quest           → クエスト内容
  initialPosition → spawn 位置 (from request)
  questVector     → 探索目標 (from quest)
```
