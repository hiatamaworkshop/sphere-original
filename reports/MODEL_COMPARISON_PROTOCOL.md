## 背景

**問題**: 現在の実行時間 ~1分/セッションは長い
**仮説**: 0.5B モデルでも種族性（性格差）は保たれる
**根拠**: 性格は Loadout (測定器具) に宿り、LLM は感覚器官にすぎない

**設計原則（EMERGENT_PERSONALITY_MEMO.md より）**:
```
性格 = 測定器具 (Loadout) × 物理法則 (Sphere) × 感覚器官 (任意の LLM)
```

→ LLM の役割は「summary を読んで h/w/d を出力する」のみ
→ 理論上、1B 未満でも指示に従えれば性格差は出る

## 評価観点

### 1. 実行時間

**目標**: 現状 (60s) の 50% 削減 → 30s 以下

**測定方法**:
- Explorers UI の Status 表示を目視確認
- 🚀 Launch Agent → ✅ Complete までの時間

**注意点**:
- 初回実行はモデルロード時間が含まれる（2回目以降で測定）
- Sphere の負荷状態に依存（ノード数が多いと遅い）

### 2. 種族性（性格差）

**測定方法**:
- hunter の avgH と balanced の avgH を比較
- scholar の avgW と balanced の avgW を比較
- 差が >1.0 ポイントなら明確な種族性あり

**失敗パターン**:
- 全種族で avgH/avgW/avgD がほぼ同じ → 評価が無意味
- 全て 10 or 0 → モデルが JSON を無視している

### 3. スコアの妥当性

**正常範囲**:
- avgH: 3.0-8.0 (低すぎるとノードが消える、高すぎると全部生き残る)
- avgW: 3.0-9.0 (知識の重みを反映)
- avgD: 2.0-5.0 (decay score は控えめな傾向)

**異常パターン**:
- 全て 10 → モデルが「良いものは全て 10」と過剰評価
- 全て 0-2 → モデルが厳しすぎる or 指示を誤解
- 標準偏差 <0.5 → 評価の分解能が低い

## チューニングは後回し

**現在のフェーズ**: 純粋なモデル入れ替え

**チューニングしていないもの**:
- ❌ num_ctx (コンテキストウィンドウサイズ)
- ❌ temperature (ランダム性)
- ❌ evalFocus (評価プロンプト)

**理由**: 変数を1つに絞る → モデルの差だけを観測

**次のフェーズ** (モデル確定後):
1. num_ctx を 512 に削減 (summary ~300 chars + 指示なので十分)
2. evalFocus を簡素化 (0.5B が理解しやすい表現に)
3. temperature を調整 (必要なら)

---

## 失敗時の対応

### ケース A: スコアが全て 10 or 0

**原因**: モデルが format:json 指示を無視、または過剰評価

**対策**:
1. evalFocus を簡素化 (複雑な指示を削除)
2. format:json を削除 → パーサーで数値抽出
3. temperature を下げる (0.3 → 0.1)

### ケース B: 種族差が消失

**原因**: モデルが evalFocus の細かい指示を理解できない

**対策**:
1. evalFocus を「heat のみ評価」「weight のみ評価」に単純化
2. Loadout の qualityVector の差を大きくする (hunter: [10,0,0])
3. より大きいモデルに切り替え (1B → 2B)

### ケース C: 実行時間が変わらない

**原因**: 推論以外のボトルネック (Sphere API, ネットワーク)

**対策**:
1. Sphere のノード数を確認 (多すぎると sense() が遅い)
2. Docker ネットワークの遅延を確認
3. num_ctx 削減を試す (後回しにしない)
