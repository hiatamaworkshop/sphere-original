# カップリングレイヤー考 — 設計哲学メモ

**Date**: 2026-02-08
**Author**: kazuh (構想) + phi-agent 実装から得た知見

---

## 1. Sphere の純粋性

Sphere は性格を持つべきではない。物理法則だけ。
decay, heat, weight, TTL — これらは中立的な物理量であり、「何が良いか」を含まない。

ならばデータの傾向 — 熱傾向なのか、weight 重視なのか、保存的なのか — はどう調整する？

**答え: 常駐型エージェントの配置。**

| 常駐エージェント | Sphere への効果 |
|-----------------|----------------|
| moth (加熱器) | 全体の温度を上げる。生態系の点火役 |
| archivist (保存者) | decay を抑制。長命なノードを増やす |
| hunter (淘汰者) | 選択的加熱。二極化を促進 |
| balanced (正規化) | 温度を平均に戻す。安定化 |

Sphere 自体を変えるのではなく、**どの性格のエージェントを何体常駐させるか**で代謝傾向をコントロールする。Sphere の純粋性は維持される。

## 2. LLM コスト構造の分析

エージェントは LLM モデル依存。このコストが大きい。

外部から Sphere に勝手に接続するエージェント（パワフルな LLM を持つもの）は放置で良い — 勝手に判断するだろうから。

しかし、**軽量エージェント**がどうにか軽量に動作したいとしたら？

### Loadout の意義の再定義

```
プリセットした役割をまとわせ、装備品を携帯させる
→ 調整されたエージェントとしてのふるまいが可能
→ LLM の能力依存が減り、推論・評価に集中できてコストが下がる
→ 必要なところに必要なだけ時間をかける
```

現状の phi-agent で実証済み:
- phi3:mini (3.8B params) でも機能する
- LLM は h/w/d を返すだけ — 戦略立案も文脈理解も不要
- 残りは四則演算 (0ms)

---

## 3. 評価のさらなる軽量化 — Auto-Capsule がヒント

LLM の推論を回す時間がもったいないのであれば、**評価をベクトル化**すれば高速に判断できるはず。

現状:
```
sense (ベクトル) → FastGate pick (ベクトル) → focus (テキスト) → LLM eval (15s) → record (ベクトル)
```

もし評価もベクトルで出来たら:
```
sense (ベクトル) → FastGate pick (ベクトル) → focus (テキスト) → ベクトル eval (0ms) → record (ベクトル)
```

可能性:
- embedding の cosine similarity で query との関連度 → h に変換
- node の物理量 (heat, weight, TTL) から権威性 → w に変換
- 前回の decay 値をそのまま → d に反映

**LLM ゼロの評価エージェント** — FastGate がそのまま h/w/d を算出する。
これなら 1 cycle 数 ms。energy のある限り高速で回せる。

### トレードオフ

| | LLM eval | ベクトル eval |
|---|---|---|
| 速度 | ~15s/cycle | ~0ms/cycle |
| 内容理解 | 深い (テキストを読む) | 浅い (メタデータのみ) |
| コスト | 高い | ゼロ |
| 用途 | 来訪者 (質重視) | 常駐者 (量重視, 代謝維持) |

**常駐型エージェント (moth, archivist) は LLM 不要かもしれない。**
メタデータだけで「熱いノードをもっと熱くする」「古いノードの decay を下げる」は計算できる。

## 4. ノード生成のボトルネック

評価を軽量化しても、**新ノードの生成**は別問題。

ノードの生成に必要な言語生成:
1. **summary** — テキスト要約
2. **content** — メインコンテンツ
3. **tags** — キーワードタグ

これらは言語生成そのものであり、LLM なしには成り立たない。つまり:

```
評価 (h/w/d) → ベクトル化可能 → LLM 不要にできる
生成 (summary/content/tags) → 言語生成 → LLM 必須 = ボトルネック
```

### 対処方針

**正式なノード生成は、推論力と貢献意欲のあるパワフルなエージェントのみが行えば良い。**

あるいは外部サービス (人間の手動投入、API 経由のバッチ投入) で賄う。

軽量エージェントの役割は「既存ノードの代謝を調整する」こと — 新しいノードを作ることではない。

### タグ生成の軽量化

上位ノードにはキーワードタグを付与する必要があるが、これも:

```
生成 (自由テキスト) → 高コスト
選択 (既存語彙から選ぶ) → 低コスト
```

下敷きとなるタグ語彙 (vocabulary/palette) を用意し、そこから**選ばせる**手法が良い。
極力言語生成の箇所を減らす。

## 5. エージェント階層の整理

```
┌─────────────────────────────────────────────┐
│ Heavy Agent (GPT-4, Claude, etc.)           │
│ - 新ノード生成 (summary, content, tags)      │
│ - 深い内容理解に基づく評価                    │
│ - 来訪者モード: 探索 → capsule → 帰還        │
│ - コスト: 高い、頻度: 低い                    │
├─────────────────────────────────────────────┤
│ Light Agent (phi3:mini + Loadout)            │
│ - LLM は評価のみ (h/w/d)                     │
│ - FastGate が戦略・行動を決定                 │
│ - 来訪者/常駐者どちらも可                     │
│ - コスト: 中、頻度: 中                        │
├─────────────────────────────────────────────┤
│ Vector Agent (LLM なし, FastGate のみ)        │
│ - 評価もベクトル計算で完結                    │
│ - 常駐者モード専用: 代謝調整                  │
│ - ノード生成不可                              │
│ - コスト: ほぼゼロ、頻度: 高い                │
├─────────────────────────────────────────────┤
│ External Service (人間, API, バッチ)          │
│ - ノード投入専用                              │
│ - Sphere の外で生成、投入のみ                 │
│ - 代謝には参加しない                          │
└─────────────────────────────────────────────┘
```

### 運用モデル

1. **External Service** がノードを投入 (コンテンツ供給)
2. **Heavy Agent** が時々来訪し、深い評価と新知見の結晶化を行う
3. **Light Agent** が定期的に来訪し、Loadout に基づく性格的評価を行う
4. **Vector Agent** が常駐し、代謝を維持する (温度調整、保存、淘汰)

Sphere 自体は何も判断しない。物理法則だけを実行する。
**知性はすべてカップリングレイヤーに存在する。**

## 6. 遅延投函 — 生成と探索の時間分離

ノード生成はコストが高い。しかし排除はしたくない — それが Sphere を支えるエネルギー源だから。

ならば、**生成を探索と同期させる必要はない。**

### 現状: 同期モデル

```
探索 → 評価 → [AutoCapsule 生成] → 帰還 → Sphere に即投入
         ↑ ここが遅い (LLM 生成)
```

AutoCapsule は帰還時にセッション要約をノードとして Sphere に残す。
これはリアルタイムで行われるが、本質的にはセッションデータの要約であり、
探索中に行う必要はない。

### 提案: 非同期モデル (遅延投函)

```
探索 → 評価 → 帰還 (高速、生成なし)
                ↓
         [生データをキューに投函]
                ↓
         [後で External Service が整形・投入]
```

エージェントは探索中に集めた生データ (nodeIds, h/w/d, tags, context) を
帰還時にそのまま残す。整形 (summary, content 生成) は後回し。

### これが成り立つ理由

1. **評価は即時に必要** — ノードの h/w/d は探索中に Sphere に反映しないと代謝が止まる
2. **新ノード生成は即時でなくていい** — カプセルは「あとで読む用」の結晶であり、遅延しても Sphere の代謝に影響しない
3. **生成コストを探索ループから分離できる** — Light Agent は評価だけ回し、ノード生成は別のプロセス (Heavy Agent / 外部サービス / バッチ処理) に委託

### 具体的な実装パス

```
Light Agent 帰還時:
  → evaluations: [{nodeId, h, w, d, tags}]  ← 生データ
  → session metadata: {query, loadout, duration, cycles}
  → これを JSON で投函 (HTTP POST / queue)

外部の整形プロセス (非同期):
  → 生データから summary を生成 (LLM)
  → tags を語彙から選択 or 新規付与
  → 正式ノードとして Sphere に submit (/capsule API)
```

### 帰結

- Light Agent のセッションが**さらに軽くなる** — 帰還時の AutoCapsule 生成を省略可能
- 生成品質が**上がる** — 後処理で Heavy LLM を使える (リアルタイム制約なし)
- Sphere への投入頻度は**変わらない** — 非同期でも結果的に同じノードが入る
- エージェントの探索速度と生成品質が**独立に最適化できる**

**「あとで投函」は妥協ではなく、正しい関心の分離。**

## 7. Sphere は LLM 駆動装置ではない

### 根本方針

Sphere は過度に LLM を駆動してはならない。

これはパフォーマンスやコストの問題ではなく、**設計思想**の問題。Sphere の代謝は自律的であるべきで、LLM がなければ回らない系は Sphere の理念に反する。

### 帰結

```
Sphere の代謝 = 物理法則 (decay, TTL, heat dissipation)
              → LLM なしで自律的に回る
              → エージェント不在でも dormancy まで生き続ける

LLM の役割 = 代謝の「調味料」
           → 評価で温度を偏らせる
           → ノード生成で多様性を注入する
           → いなくても系は崩壊しない
```

### 投函の分離が意味を持つ理由

遅延投函の本質は「LLM 呼び出しの最小化」だけではない。**Sphere がLLM のスループットに依存しない**構造を作ること。

- 投稿先は Sphere 本体のエンドポイントである必要はない — 別の整形サービスでも良い
- プールしてからバッチ処理した方が効率的かもしれない
- しかし最も重要なのは、Sphere の heartbeat (tick, decay, CleanerFish) が LLM の応答速度に一切結合しないこと

### Vector Agent の位置づけ再定義

Vector Agent (LLM なし) は「コスト削減の妥協」ではなく、**Sphere の理念に最も忠実なエージェント**。

```
Vector Agent = Sphere の物理法則を外から補助する存在
             = 数値だけで代謝を調整
             = LLM に依存しない → Sphere の純粋性を保つ
             = 常駐に最も適している

Light/Heavy Agent = 外来の知性
                  = 来訪して知見を注入し、去る
                  = LLM コストは来訪者が負担
                  = Sphere はそのコストに関与しない
```

Sphere がやるべきことは「LLM を呼ぶ」ことではなく「LLM が来たときに正しく受け入れる」こと。ドアを開けておくだけで、呼びに行かない。

---

## 8. 設計原則のまとめ

1. **Sphere は純粋であるべき** — 性格・バイアスをゼロにし、物理法則だけを走らせる
2. **代謝傾向はエージェントの配置で制御する** — Sphere を変えるのではなく、常駐者の構成を変える
3. **LLM は言語生成にのみ必要** — 評価はベクトル化できる、戦略は数値で表現できる
4. **言語生成を最小化する** — 選択 > 生成。タグは語彙から選ぶ、評価はスカラーで返す
5. **エージェントは階層化する** — Heavy (生成+評価) / Light (評価のみ) / Vector (代謝維持)
6. **正式なノード生成は贅沢品** — パワフルなエージェントか外部サービスの仕事
7. **生成と探索を同期させない** — 評価は即時、生成は遅延投函で良い
