# LLM as Judgment Element — Coupling Layer Architecture Memo

**Date**: 2026-02-08
**Context**: phi-agent の設計を俯瞰して抽出した一般原則

---

## カップリングレイヤーが Sphere にもたらす機能

### 1. 代謝の駆動力

Sphere は自律的に decay する — ノードは放っておけば冷えて化石化し、最終的に消える。エージェントの evaluate が**唯一の加熱源**。phi-agent は Sphere の心臓のポンプ役で、何に注意を向け、何を評価するかが生態系全体の温度分布を決める。

moth が入れば全体が加熱する。archivist が入れば decay が抑制される。hunter が入れば一部だけが極端に加熱する。**同じ Sphere が、接続するエージェントの性格で違う生態系になる。**

### 2. 淘汰圧の供給

evaluate で h<5 を与えれば冷却、d を高くすれば decay 加速。これは「何が生き残るべきか」の判断を Sphere の外から注入すること。Arbiter は物理量しか見ないから、淘汰の**意味的判断**はカップリングレイヤーだけが担う。

### 3. 情報の結晶化

帰還時の AutoCapsule は、エージェントが見たものの要約を Sphere に残す。探索行為自体が Sphere のコンテンツを増やす — **観測が新しいノードを生む。**

## 一般原則: LLM を「推論マシン」から「判断素子」に降格する

### 従来の LLM エージェント設計

```
LLM が全部決める:
  何を見るか → LLM が推論
  どう評価するか → LLM が推論
  次にどう動くか → LLM が推論
  いつ帰るか → LLM が推論
```

### phi-agent の設計

```
LLM は 1 箇所だけ:
  何を見るか → FastGate + Weapon (数値計算, 0ms)
  どう評価するか → phi (LLM, ~15s) ← ここだけ
  次にどう動くか → Feelings × chooseAction (4D内積, 0ms)
  いつ帰るか → returnDesire (4D内積, 0ms)
```

LLM は「このノードの内容は良いか？ h/w/d で答えろ」しか聞かれない。文脈理解も戦略立案も求められない。**純粋な知覚器官**として使っている。

---

## なぜこれが意味を持つか

### 1. 性格が LLM の外に出た

従来: 性格 = system prompt の文言。「あなたは慎重な研究者です」と書く。
phi-agent: 性格 = 4D ベクトル × 4 本。`[0.3, 0.2, 0.1, 0.4]` と書く。

system prompt での性格は不安定 — モデルが変われば振る舞いが変わる。ベクトルでの性格は決定論的 — モデルに依存しない。evalFocus が唯一の prompt 上の性格だが、これも出力の**重み付け**を変えるだけで、戦略を変えるものではない。

### 2. LLM の不確実性が局所化された

phi の出力が h=5 でも h=9 でも、その後の行動選択は deterministic。LLM のハルシネーションや気まぐれが、システム全体の振る舞いを壊さない。最悪 phi が全部 h=5 を返しても、エージェントは feelings の staleness で帰還する。**LLM が壊れても系は崩壊しない。**

### 3. コスト構造の逆転

LLM 呼び出しは高い (時間・compute)。従来のエージェントは cycle あたり 2-5 回 LLM を呼ぶ。phi-agent は 1 回。残りは四則演算。これは phi3:mini のような小型モデルでも実用的に動く理由でもある。

**LLM に聞くべき問いを最小化し、聞いた答えを数学的に増幅する。**

## レイヤー構造

```
判断素子 (LLM)
  ↓ スカラー出力 (h, w, d)
フィルタリングレイヤー (Weapon, FastGate)
  ↓ ノード選択
性格レイヤー (Loadout: qualityVector, returnWeights)
  ↓ 感情 → 行動
物理レイヤー (Sphere)
  ↓ 状態遷移
```

- LLM は最上位のセンサー
- その下の全レイヤーは LLM 非依存で交換可能
- Sphere を外して別のデータストアに繋いでも、Loadout のベクトル体系はそのまま使える
- LLM を GPT-4 に変えても FastGate は書き換え不要

### 交換可能性マトリクス

| レイヤー | 交換時の影響範囲 | 再設計が必要なもの |
|----------|-----------------|-------------------|
| LLM (phi3 → GPT-4) | evalFocus の prompt 調整のみ | なし |
| データストア (Sphere → 別DB) | SphereClient の実装のみ | sense/focus の返り値型 |
| 性格 (Loadout 追加) | JSON に 1 エントリ追加 | なし |
| 行動 (新 action type 追加) | chooseAction に 1 分岐 | Loadout に対応パラメータ |

## 設計原則の要約

1. **LLM はセンサーであり、コントローラーではない** — 知覚だけを担当させ、判断と行動は数学に委ねる
2. **性格は数値で表現する** — prompt engineering ではなく、ベクトル空間上の点として定義する
3. **不確実性を局所化する** — LLM 出力のブレがシステム全体に伝播しない構造にする
4. **LLM 呼び出しを最小化する** — 1 cycle 1 call。残りは 0ms の決定論的計算
5. **レイヤー間の結合を型で縛る** — LLM → スカラー(h,w,d) → ベクトル(feelings) → 行動(enum)。各境界が明確

---

## Sphere 依存性と汎用性

この設計は Sphere に依存する実装だが、原則は汎用的:

- 「代謝する環境 + 判断素子としての LLM + ベクトル性格」の三層構造は、任意の探索タスクに適用可能
- ノードの h/w/d を返す代わりに、ドキュメントの relevance/quality/freshness を返す LLM でも同じ構造が使える
- Loadout の 4D ベクトル体系は、探索以外の意思決定 (推薦、フィルタリング、優先順位付け) にも転用できる

**核心は「LLM に何を聞くか」の設計。聞く量を減らし、聞いた答えの活用を最大化する。**
